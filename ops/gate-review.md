# Offline gate review

`sudetect.gate_review.review_gate(body, content_type, url, scope, capability=None)` accepts **already fetched** bytes. It never fetches, submits, authenticates, or follows links. The callable returns only status, independent gate/auth/data fields, SHA-256 evidence references, bounded category names, and follow-up codes. It never returns passwords, page text, URLs, field values, screenshots, or exceptions. An HTML response can be inspected statically without a gate capability; status stays `pending` and reason is `capability_required`. Scope authorization is always checked first. With a permitted capability, isolated replay is attempted by default when the page has a supported inert projection; pass `replay_browser=False` for a static-only pass.

The capability is separate from the anonymous probe policy. The recommended scope-wide form has `policy_id`, `action`, `valid_until`, and `authorization_ref`; one approval covers newly found pages that the current `Scope` authorizes. It does not authorize another policy, origin, or path. The legacy pinned form remains compatible and binds an exact canonical target URL, `policy_id`, ownership evidence reference, action, UTC expiry, one attempt maximum, and captured response SHA-256. In either form the engine binds each execution to policy, canonical target, and captured bytes through `review_binding_sha256` and `response_sha256`. Store capability files only in the private case area.

```json
{"policy_id":"approved-policy", "action":"reveal_delivered_content", "valid_until":"2030-01-01T00:00:00Z", "authorization_ref":"owner-approval-reference"}
```

The one-attempt limit applies to a single call. The audit scheduler must persist attempt consumption keyed by capability/authorization reference and job before calling this helper for a cumulative limit across processes or retries. An in-flight crash after reservation may consume an attempt without a result; retry policy must account for that. This module does not keep its own durable ledger.

Supported actions are `reveal_delivered_content` and `verify_fixed_client_gate`. The latter recognizes exactly one simple inline handler: read `#password`, compare it with one fixed literal, remove `#login-screen`, and set `#app` display to `flex`. The literal is never returned. With `replay_browser=True`, that allowlisted handler is executed once in a fresh isolated context using the fixed literal; only then can `client_gate_tested` be true. It does not test a live form or server authentication. Without a browser run, `client_gate_tested=false` and the result is partial. Other code is `unsupported_client_gate`, with a controlled broker/manual review follow-up. No password guessing, reuse, or server bypass is implemented.

A hidden, filled business payload or hidden input value in the initial HTML can be classified from the original response without requiring `#login-screen` or `#app`. Counts and category evidence are returned without values. For a generic inline hidden text region, the engine builds a new bounded HTML projection from escaped text; it discards the original scripts, CSS, links, and form actions. `replay_source=sanitized_hidden_text_projection`, `original_dom_replayed=false`, and `original_active_content_stripped=true` when active content was present make this distinction explicit. Filled input attributes are static evidence only because their values are intentionally omitted from the projection. CSS visibility is recognized only for explicit inline `display:none`, `visibility:hidden`, and the `hidden` attribute; stylesheet-derived visibility remains unverified.

The inert projection is validated with `dom_replay` rules; supported pages attempt a fresh Chromium context with request routing blocked, service workers blocked, dead proxy, and zero accepted network requests. Plain reveal disables JavaScript. The fixed handler path runs only the recognized script against a sanitized structure projection and still requires the exact `#login-screen`/`#app` pattern. Unknown client JavaScript is never executed. Browser failure leaves a pending result with a fixed reason and no exception text. A successful generic projection display proves only that text already in the response can be displayed locally; it is not a reproduction of the original UI or an authentication result. `server_authorization_tested` always remains false. If a server request, encrypted content, or an empty template is observed, its data remains unobserved until a separate authorized mechanism evaluates it.

The independent result fields are `auth_ui_present`, `client_secret_literal_present`, `request_present`, `login_request_present`, `payload_in_initial_response`, `payload_template_only`, `encrypted_payload_observed`, `client_gate_tested`, `server_authorization_tested`, `actual_data_access_result`, and `business_logic_evidence_refs`. `client_secret_literal_present` is a static source-code candidate, including common password assignments/comparisons; it does not mean the strict executable handler matched. `request_present` includes generic API calls, while `login_request_present` requires a login/auth/session endpoint signal. Neither proves a request was sent. Category evidence references use the response hash and a non-value category. They are candidates; they do not prove sensitivity or approval status. The gate parser caps input at 4 MiB and also honors `scope.max_bytes`. Large, non-UTF-8, unknown, or unsafe structures stay pending.

CLI entry: `python -m sudetect.gate_review --response CAPTURE.html --scope SCOPE.json --capability CAPABILITY.json --target-url https://example.test/app --output REPORT.json [--no-replay-browser]`. The response and manifest must be local regular files without symlink/reparse ancestors. The output must be new and in an existing directory. Errors print only a fixed code. The main audit CLI also registers `gate-review`.

No live input submission path is provided. A future controlled broker must validate the exact request destination, redirect chain, method, body, side effects, and one-attempt budget against the capability before making a request. External IdP, CAPTCHA, MFA, and server credentials require separate capabilities and remain pending here.
