# 공통 감사 실행 절차

정본은 [영문 절차](../../ops/audit-workflow.md)다. Codex, Claude, CLI 작업자는
같은 Python 엔진·명령·상태·완료 기준을 사용한다. 모델 버전이나 추론 수준을
고정하지 않는다.

1. seed·소유 근거·제외·권한을 비공개 입력으로 기록한다. 독립 발견에서는 held-out
정답 파일을 읽지 않고, 기존 자산 재점검은 recheck로 구분한다.
2. doctor로 실행 코드 일치를 확인하고 실제 메타데이터 탐색 전에 채널 control을
확인한다. 이름 유사성이나 seed에서 유도한 prefix는 소유 증거가 아니다.
3. case를 한 번 생성하고 같은 case를 인계·재개한다. scope는 재개 때 다시 검사하며
자동 갱신하지 않는다.
4. 승인된 한도 안에서 실행 가능한 작업을 진행한다. 실패 채널·잘린 파일·의존성
부재를 정상 결과로 처리하지 않는다. 미완료·차단·재시도 대기 작업을 보존한다.
5. 접근·자료 분석·공개 승인·서버 인증을 각각 검토한다. 화면 표시만으로 서버
인증 우회를 주장하지 않는다.
6. 원장에서 보고서를 만들고 실제 실행·검증과 미실행 항목을 구분해 보고한다.
   유한한 자산 목록에서 전체 회사 범위를 주장하지 않는다.

현재 주 에이전트의 선택 모델은 작업 중 바꾸지 않는다. 사용 가능하면 Sol/Sonnet은
범위가 분명한 독립 분석에, Luna/Haiku는 입력·출력이 정해진 추출·정규화·집계에
적합하다. 모호한 해석과 최종 판단, 결과 통합은 주 에이전트가 맡는다. Astra 계열은
사용자가 직접 선택하거나 명시적으로 요청한 경우에만 사용한다. 공개 데이터 조사도
동일한 승인 범위·예산 안에서 독립 작업으로 맡길 수 있다. 위임은 권한을 넓히지 않으며
작업자는 파일과 작업을 나눠 소유한다.

`audit init/plan/run/resume/status/report/evaluate` 명령과 예산 항목은 정본 예제를
따른다. `--agent`는 작업자 표시다. 매 실행 구간의 예산은 승인된 요청·다운로드 예약·
분석 바이트·시간·시도·작업 수로 제한한다. 예약량과 실제 수집량을 구분하고, 재요청은
새 시도로 계산한다. transient 또는 명시적으로 선택한 오류만 새로 승인된 구간의 예산
안에서 재시도한다. 해결되지 않은 입력·영구 실패·retry_wait를 정상으로 바꾸지 않는다.

저장된 seed plan을 version 2로 올릴 때 누락 prefix 작업은 멱등하게 추가하고
완료된 작업은 보존한다. `engine_review_version`이 없는 기존 성공 캡처는 현재
scope·예산 안에서 `engine-review:2:asset` 중복 방지 키로 한 번 재검토한다. 같은
엔진 검토 버전으로 재개할 때 자산을 다시 fetch하지 않는다.

현재 승인 범위의 저장소 후보마다 관측된 branch에서 최대 5개 commit
(`per_page=5`)을 예산 안에서 요청할 수 있다. 관측된 SHA는 동일한 scope 안에서
`repository_tree` 작업으로 큐에 넣는다. 최신 구간만 보는 제한이 있으므로
`history_window_not_exhaustive` 공백을 유지한다. 과거 전체 이력이나 삭제된 자료를
전수 확인·복구한 것으로 설명하지 않으며, scope나 예산을 자동으로 넓히지 않는다.

기존 Ledger와 LocatorStore를 사용한다. 만료 lease와 시도별 토큰으로 오래된 작업자의
완료 요청을 차단한다. CLI는 서비스를 설치하거나 대화 종료 뒤 자동 실행하지 않는다.
case에는 비공개 seed·locator가 있으므로 저장소에 공개하지 않고, 원문·비밀·마스킹되지
않은 개인정보를 로그나 보고서에 복사하지 않는다.

가시·숨김 본문, 표, 계산식, 정적 자료와 지원 문서를 검토한다. 실제 값·템플릿·필드명을
구분하고, 정적 JavaScript JSON은 제한된 구조·범주 요약으로만 반영한다. 원시 리터럴을
보고하지 않으며 잘림·파싱 한계는 미완료로 남긴다. 문서의 literal 참조는 후속 검사 후보일
뿐, 문서가 실제로 가져와 검토됐다는 뜻은 아니다.

PDF는 분석 페이지·페이지별 텍스트/이미지 상태와 OCR 상태를 따로 기록한다. 이미지가
있거나 텍스트가 비어 있는 페이지의 OCR 상태는 `not_run`일 수 있다. 이 절차가 OCR을
자동 실행하지 않는다. inline base64 이미지 payload는 스트리밍 분석 투영에서 분리하고
나머지 수집 바이트를 분석할 수 있다. 원본 응답은 승인된 수집 한도 안에서만 받고 일시
보관하며, 투영은 최대 4 MiB다. 기본 수집 한도는 256 KiB이고, `max_bytes`를 명시하면
최대 128 MiB까지 설정할 수 있다. 이 설정은 승인된 scope·예산을 자동 확대하지 않는다.
투영에서 이미지가 빠지면 미디어/OCR 공백을 남기며, 텍스트 분석이나 투영만으로 이미지
검토·OCR 완료를 주장하지 않는다.

gate parser는 4 MiB로 제한한다. 원본 응답이 이 한도를 넘으면 전체를 파싱한 것처럼
표시하지 말고 공백을 기록한다.

수집, 텍스트/분석, 구조, 미디어, 게이트, 민감도, 공개 승인, 서버 인증 상태를 서로 독립된
검토 차원으로 유지한다. `NOT_INSPECTED`, 해당 없음, 부분, 미확인을 합치지 않는다.
`case_status.complete`는 제한된 예약 작업의 완료 상태다. 큐가 완료되고 search plan에
남은 일이 없으며, 최신 대상에 gap이 없고 수집·분석이 완료된 경우를 뜻한다. 회사 전체
범위, 공개 승인, OCR, 게이트 실행, 서버 인증을 뜻하지 않는다. 각 차원과 남은 공백을
별도로 보고한다.

익명 probe/browser와 별도 gate-review capability의 경계를 지킨다. gate-review는 정확한
대상·capability가 승인된 경우에만 진행하며 임의의 게이트 실행이나 과거 이력 통합을
주장하지 않는다. 서버 인증 시험은 별도 조건이 필요하다. 인계에는 case 경로·실행 ID·현재
상태·증거·남은 공백을 포함한다. 합성 검증을 실제 서비스 점검으로 설명하지 않는다.
# 외부 발견 채널 결과 연결

GitHub 메타데이터는 audit 실행기가 처리한다. 다른 지원 채널은 기존
`channel-discover`에 제공자·JSON export 설정과 최신 채널 점검 결과를 전달한다.
연결되지 않은 채널은 검색 완료로 처리하지 않는다. `--locator-store`에는 같은
case의 `locators.sqlite`를 쓰고, 설정의 work ID·검색어는 해당 case의
`search-plan.json` 항목과 일치시킨다. 실제 실행 보고서는 다음 명령으로 반영한다.

```sh
open-detective audit import --case _local/new-case --input _local/channel-report.json --channel-health _local/health.json
```

검색어·채널 근거·개수·모든 opaque 참조를 검증한 뒤 후보를 큐에 넣는다.
부분 결과는 미완료로 유지하며 새 후보의 소유나 접근 권한을 자동 부여하지 않는다.
중단된 import를 반복해도 후보와 시도 이력이 중복되지 않는다. resume은 완료된
채널 검토를 반영하고 현재 scope가 허용한 후보를 검사한다. 운영 import는 합성으로
표시된 보고서를 거절하지만, 로컬 메타데이터는 편집 가능하므로 실제 실행의 독립
증명은 아니다. 운영자 제공·실행 미검증 근거라는 한계를 보고서에 남긴다. 과거
관측은 최신 채널 상태를 덮어쓰지 못한다. 외부 채널 요청은 별도의 명시적 scope·예산을 사용하며 audit
구간의 요청 수로 합산하지 않는다. case별 발견 실행기는 하나만 실행하고 import나
검색 계획 변경 전에 중지한다. 콘텐츠 작업에는 원자적 lease를 적용한다.
