# 위험 분류 — 열려 있는 것과 유출된 것을 구분한다

**"자산이 열려 있다"와 "자료가 유출됐다"는 다른 사실이다.** 이 둘을 섞으면 보고가 무너진다.
과장하면 신뢰를 잃고, 축소하면 조치가 늦는다.

> 선례: 2026-07 감사에서 저장소는 공개였지만 비밀번호 하드코딩은 없었고
> 차량 데이터도 HTML에 없이 API에서 받아오는 구조였다. **"공개 = 데이터 전량 유출"이 아니었다.**
> 이 구분을 지켰기 때문에 보고가 정확했다.

## 등급

| 등급 | 내용 | 조치 시한 |
|---|---|---|
| **S** | 유효 자격증명(API키·토큰·비밀번호·인증서 개인키) | 즉시 — **교체 먼저** |
| **A** | 개인정보 (성명·연락처·주소·생년월일·면허·계좌·차량번호·계약정보) | 즉시 — **CPO 에스컬레이션** |
| **B** | 기밀 사업정보 (단가·원가·수익구조·경쟁사 분석·계약조건·미공개 계획) | 당일 |
| **C** | 내부 구조 노출 (API 주소·서버 구성·관리 기능 동작·내부 경로) | 주 단위 |
| **D** | 브랜드·구성 노출만 (회사명·화면 구성) | 정리 대상 |

**고유식별정보(주민등록번호·여권번호·운전면허번호·외국인등록번호)가 포함되면 A를 S와 같은 시급도로 다룬다.**
렌터카 업종에서 면허번호는 상시 취급 대상이라 실제로 자주 해당한다.

## 판별 순서

```
① 자산이 익명에게 열려 있는가            → ops/verify.md
② 열려 있다면 그 안에 무엇이 있는가       → 아래 ③~⑤. 내용 열람은 최소화한다
③ 파일 목록(메타데이터)으로 1차 분류      → git/trees, 디렉터리 목록
④ 위험 확장자·파일명 패턴 표시            → 아래 표
⑤ 개인정보 징후가 보이면 즉시 중단        → 원칙 11. CPO로 넘긴다
```

**③에서 멈출 수 있으면 멈춘다.** 파일 내용을 받지 않고도 우선순위는 매겨진다.

## 1차 분류 신호 — 파일명·확장자

| 신호 | 함의 |
|---|---|
| `.env` · `.mcp.json` · `.cursorrules` · `CLAUDE.md` · `.claude/settings.json` | **AI 에이전트 설정.** 내부 URL·접속정보·키가 한 파일에 응집 |
| `config.*` · `*.yaml` · `*.ini` · `credentials` · `*.pem` · `*.key` · `*.p12` | 자격증명 가능성 |
| `*.json` · `*.csv` · `*.xlsx` · `*.sql` · `*.db` · `*.bak` | **데이터 파일.** 개인정보·기밀 적재 가능성 |
| `*.pdf` · `*.hwp` · `*.hwpx` · `*.docx` · `*.pptx` | 문서. **§파일 내부 검사 필수** |
| `*.map` | 소스맵 — 프론트 원본코드 복원 |
| `backup`·`old`·`bak`·`temp`·`test` 포함 파일명 | 정리되지 않은 잔존물 |

> 판단 기준(선례): **설정·데이터 파일이 든 저장소가 가장 위험하다.**

## 파일 내부 검사 — 찾은 파일 안에 무엇이 남았나

"어디서 찾나"만으로는 부족하다. 확보한 파일에 대한 **필수 후속 단계**다.
공개된 파일 수가 적어도 **한 건이 대량 레코드를 담을 수 있어** 피해 기댓값이 크다.

| 형식 | 확인할 것 |
|---|---|
| 엑셀 | 숨김 시트 · 숨김 행/열 · 피벗캐시 · 필터로 가려진 데이터 · 수식이 참조하는 외부 경로 |
| PDF | **검은칠(redaction) 실패** — 사각형 아래 원문이 그대로 남음 · 문서 속성 · 주석 |
| HWP·HWPX | 작성자 · 소속 · **내부 NAS 경로** · 편집 이력 |
| 이미지 | **EXIF GPS**(차고지·정비소 위치) · 촬영 단말 · 촬영 시각 |
| Office 전반 | 작성자 · 최종 수정자 · 회사명 · 템플릿 경로 |

**원본을 복제해 로컬에 보관하지 않는다**(원칙 10). 검사는 최소·마스킹, 조치 후 파기.

### 구조화 데이터 — 필드가 있다는 것과 값이 있다는 것은 다르다

JSON·API 응답에서는 **필드명만 보고 유출을 단정하지 않는다.** 스키마에 민감한 이름이 있어도
값이 전부 `null`·`0`·빈 문자열이면 그 항목은 나가지 않는 것이다. 반대도 성립한다 —
평범한 이름의 필드가 대량 레코드를 담고 있을 수 있다.

**필드별 채움율을 집계해 확정한다.** 이는 개별 값 열람이 아니라 집계이므로 원칙 10·11과 충돌하지 않는다.
등급표에 올릴 것은 **값이 실제로 들어 있는 필드**뿐이다.

> 이 단계가 없어서 오판한 선례가 있다. 원가·수수료율·잔가 필드가 스키마에 있어 "수익구조 유출"로
> 1차 보고했으나, 집계해 보니 해당 필드는 전부 비어 있었고 실제로 나간 것은 판매가격표였다.
> **과장은 축소만큼 보고를 무너뜨린다.**

## 확정과 미확정을 분리한다

보고서를 두 칸으로 나눈다. 섞으면 전체가 의심받는다.

**확정** — 익명 실측으로 재현되는 사실만.
> 예: "익명 GET에 200 / 약 82KB / sha256 `a1b2c3…` 본문 전량 전달"

**미확정** — 근거가 부족해 단정할 수 없는 것. **무엇을 더 측정해야 확정되는지 함께 적는다.**
> 예: "포트 9200이 외부 스캔 데이터에 열림으로 보고됨. 단 ① 해당 IP는 5개 도메인이 공유하며
> ② 스캔 데이터의 stale이 실증됨(443 누락) ③ 서비스 종류·인증 여부 미확인.
> **확정에 필요한 것**: 서버 관리주체 확인 후 호스트에서 `ss -lntp`·방화벽 정책·인증 설정 점검."

**서버 코드나 내부 접근이 없으면 서버측 방어 여부를 단정하지 않는다.**
도구가 중간에 실패해도 점검은 끝나야 한다 — **도구 실패와 판단 실패를 분리한다.**
